## 1. 项目概述

### 1.1 目标

在 12 周内完成 GeniusFlow MVP 版本的开发、测试和部署，交付可运行的 AI 驱动流程管理平台。

### 1.2 范围

**包含：**
- 流程设计器（线性顺序、任务节点、开始/结束节点）
- 节点三阶段配置（输入/行动/输出 + AI 角色）
- AI 督导（完整性检查）和审批助理（摘要+建议）
- 员工工作台（任务执行、AI 助手面板）
- 管理者工作台（审批中心、进度监控）
- 知识库管理（上传 PDF/TXT，向量检索）
- 进度管理（计划工期、手动百分比、只读甘特图）
- 模板市场（预设模板、私密模板复制）
- RBAC 权限控制（设计者/员工/管理者/管理员）

**不包含：**
- 子流程、条件分支、并行网关
- Co-pilot 内容生成、顾问问答
- 多租户 SaaS
- 移动端适配
- 外部系统集成（Webhook、CRM）

### 1.3 成功标准

| 指标 | 目标值 | 验证方式 |
|------|--------|----------|
| 核心功能可用性 | 99.5% | 监控告警 |
| 流程加载时间 | < 1s | 性能测试 |
| 节点提交响应 | < 0.5s（不含 AI） | 性能测试 |
| AI 督导准确率 | > 80% | 人工抽样评估 |
| 单元测试覆盖率 | > 70% | 覆盖率报告 |
| 严重 Bug 数 | 0 | 发布前验收 |

## 2. 团队组织

### 2.1 团队结构

```
项目经理 (PM) × 1
    │
    ├── 前端负责人 × 1
    │       └── 前端开发 × 1
    │
    ├── 后端负责人 × 1
    │       └── 后端开发 × 1
    │
    ├── AI 工程师 × 1
    │
    └── 测试工程师 × 1（Week 6 加入）

总计：6 人（全职 5 人 + 测试 1 人）
```

### 2.2 角色职责

| 角色 | 人数 | 核心职责 |
|------|------|----------|
| 项目经理 | 1 | 进度跟踪、风险管理、客户沟通、每日站会主持 |
| 前端负责人 | 1 | React Flow 技术预研、架构设计、代码审查、复杂组件开发 |
| 前端开发 | 1 | 页面开发、组件实现、接口联调 |
| 后端负责人 | 1 | NestJS 架构、数据库设计、流程引擎核心、代码审查 |
| 后端开发 | 1 | API 开发、业务逻辑、AI 服务对接 |
| AI 工程师 | 1 | FastAPI 服务、Prompt 工程、RAG 实现、模型调优 |
| 测试工程师 | 1 | 测试用例设计、自动化测试、性能测试、Bug 跟踪 |

### 2.3 沟通机制

| 会议 | 频率 | 参与者 | 时长 | 内容 |
|------|------|--------|------|------|
| 每日站会 | 每天 9:30 | 全员 | 15min | 昨日完成/今日计划/阻塞问题 |

## 7. 开发规范

### 7.1 Git 工作流

```
main        ─────●─────────●─────────●─────  生产分支
                ↑         ↑         ↑
release/v1.0  ──┘    ───●────  ───●────     发布分支
                        ↑         ↑
feature/xxx   ───●──●──┘   ──●───┘         功能分支（从 main 切出）
                    ↑        ↑
                   PR       PR
```

**分支规范：**
- `main`：生产分支，只允许合并 release 分支
- `release/v{x.y}`：发布分支，从 main 切出，测试通过后合并回 main
- `feature/{模块}-{功能}`：功能分支，如 `feature/process-designer-canvas`
- `fix/{bug-id}-{描述}`：Bug 修复分支

**提交规范：**
```
<type>(<scope>): <subject>

<body>

<footer>
```

| type | 说明 |
|------|------|
| feat | 新功能 |
| fix | Bug 修复 |
| docs | 文档更新 |
| style | 代码格式（不影响功能） |
| refactor | 重构 |
| test | 测试相关 |
| chore | 构建/工具相关 |

示例：`feat(process): 添加流程发布功能`

### 7.2 代码规范

**前端：**
- ESLint + Prettier 强制格式化
- 组件命名：PascalCase（如 `ProcessCanvas.tsx`）
- Hooks 命名：useXxx（如 `useProcessDefinition.ts`）
- 类型定义：接口名 PascalCase，属性名 camelCase

**后端：**
- ESLint + Prettier
- 模块命名：kebab-case（如 `process-engine.module.ts`）
- 类命名：PascalCase（如 `ProcessEngineService`）
- 方法命名：camelCase（如 `createProcessInstance`）

**AI 服务：**
- Black 格式化
- 类型注解（Python 3.10+）
- 函数文档字符串

### 7.3 代码审查

- 所有 PR 必须经过至少 1 人审查
- 核心模块（流程引擎、AI 服务）需 2 人审查
- 审查 checklist：
  - [ ] 功能是否符合需求
  - [ ] 是否有单元测试
  - [ ] 是否有类型错误
  - [ ] 是否有安全漏洞
  - [ ] 性能是否可接受

## 8. 测试策略

### 8.1 测试金字塔

```
        /\
       /  \
      / E2E \      ← 5%  端到端测试（Playwright）
     /────────\
    / 集成测试 \   ← 25% API 集成测试（Jest + Supertest）
   /────────────\
  /   单元测试    \ ← 70% 单元测试（Jest / pytest）
 /────────────────\
```

### 8.2 测试覆盖要求

| 模块 | 单元测试覆盖率 | 测试重点 |
|------|--------------|----------|
| 流程引擎 | > 90% | 状态机转换、节点推进 |
| AI 服务 | > 80% | Prompt 渲染、JSON 解析 |
| 用户权限 | > 80% | RBAC 校验 |
| 其他模块 | > 70% | 核心业务逻辑 |

### 8.3 测试计划

| 阶段 | 时间 | 内容 |
|------|------|------|
| 单元测试 | 开发同步 | 每功能开发时同步写单元测试 |
| 集成测试 | Week 6-9 | API 接口集成测试 |
| E2E 测试 | Week 10 | 核心流程端到端测试 |
| 性能测试 | Week 10 | 100 并发压测 |
| AI 评估 | Week 10 | 人工抽样评估准确率 |
